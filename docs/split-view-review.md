# 창 분할(스플릿 뷰) 도입 검토

> 작성: 2026-06-13 · 대상: 설계 검토(구현 아님) · 결론: **보류(Defer)**

## 1. 결론 요약

**보류.** 현재 코드/제품 단계에서 창 분할은 무게 대비 가치가 낮고, 이미 계획된
다른 기능(멀티탭 / 간단 편집 모드)과 역할이 겹친다. 다만 "두 MD를 나란히 비교"라는
유스케이스 자체는 AI-dev에 유효하므로 **완전 제외는 아님** — 멀티탭이 먼저 도입된 뒤
그 위에 얇게 얹는 순서로 재평가한다.

## 2. 현황 (실제 코드 근거)

- **상태 모델은 완전한 단일 문서 가정.** `src/store/app.ts`의 `currentFile: string | null`,
  `currentContent: string | null`, `headings`, `activeHeadingId`, `bookmarks`,
  `externalChanged`, `fileMissing` 등 문서 관련 상태가 전부 스칼라 단수. 두 번째 문서를
  표현할 자료구조가 없음.
- **뷰어는 단일 인스턴스 가정.** `src/components/viewer/MarkdownViewer.tsx`는 스토어의
  단수 상태를 직접 구독하고, 파일별 스크롤 위치(`scrollPositions`), 파일 워처
  (`useFileWatcher(currentFile, ...)`), 변경 diff(`prevSource`)를 컴포넌트 내부 ref로
  관리. 두 개를 동시에 띄우면 각자 독립된 `currentFile`/워처/스크롤 상태가 필요 → 사실상
  뷰어를 "문서 인스턴스" 단위로 재설계해야 함.
- **레이아웃은 3열 flex 경합 구조.** `src/components/layout/AppShell.tsx`는
  `사이드바(가변 160~480px) | 메인(flex-1, 중앙정렬 max 760px) | 목차(220px)`의 가로
  배치. 본문은 이미 720~760px 중앙 정렬(콘텐츠 퍼스트 원칙)이라 메인을 둘로 쪼개면 한 쪽
  본문 폭이 360px대로 줄어 가독성이 깨진다. 사이드바+목차가 동시에 열리면 분할 공간이
  거의 남지 않음.
- **상단 크롬은 의도적으로 최소.** `TopBar.tsx`는 햄버거+아이콘 몇 개 + 중앙 파일명/토큰
  표시뿐. 분할 토글/페인 포커스/닫기 버튼을 더하면 "메뉴바 없음·아이콘 3~4개" 원칙과
  직접 충돌.

## 3. 유스케이스 평가

| 유스케이스 | 평가 |
| --- | --- |
| (A) 두 MD 문서 비교 (예: 프롬프트 v1 vs v2, CLAUDE.md vs AGENTS.md) | AI-dev에 **유효**. 단 `docs/FEATURE-PROPOSALS.md`에서 이미 **Tier 3 "side-by-side diff"**로 분류된 항목 — 별도 diff 기능과 본질적으로 같은 니즈. |
| (B) 한 문서의 편집 \| 미리보기 분할 | **간단 편집 모드(Cmd+E)와 정확히 중복.** 편집 모드의 본질이 "좌측 plain text · 우측 렌더"이므로, 이를 위한 별도 "창 분할"은 불필요. |

→ (B)는 편집 모드가 흡수, (A)만 남는데 (A)는 멀티탭/ diff와 겹침.

## 4. 계획된 기능과의 관계

- **멀티탭 (제안 #9, Tier 2):** 스플릿이 의미를 가지려면 "어떤 두 문서를 띄울지"
  선택·전환 수단이 필요하고, 그 수단이 곧 탭/스위처다. **멀티탭이 선행 인프라.**
  탭 없는 스플릿은 두 번째 문서를 고르는 UX가 빈약하다(현재는 Quick Open으로 단수
  `currentFile`만 교체). 즉 스플릿은 멀티탭의 **상위 기능**이지 독립 기능이 아니다.
- **간단 편집 모드 (Cmd+E):** 위 (B)를 담당. 편집|미리보기 분할은 편집 모드 안에서
  국소적으로 해결할 문제이지 범용 창 분할로 풀 문제가 아니다. **중복.**
- **변경 하이라이트(구현됨) + 폴더 검색/Quick Open(신규):** 이미 "AI가 뭘 바꿨나"를
  같은 문서 안에서 추적하는 경량 수단을 제공. 두 문서 비교 수요의 상당 부분을 흡수한다.

## 5. 원칙 충돌 / 무게 평가

- **콘텐츠 퍼스트 미니멀:** 본문 폭이 핵심 자산인데 분할은 본문을 좁힌다 → 정면 충돌.
- **기능 과잉 금지:** 스플릿은 단독 기능이 아니라 멀티탭+포커스 관리+페인 리사이즈+
  페인별 워처/스크롤/검색 상태를 끌고 오는 **시스템급 변경**. `FEATURE-PROPOSALS.md`가
  스스로 분류한 "여러 파일을 동시에 훑는 무거운 기능" 범주에 속한다.
- **무게:** 🟠~🔴. 스토어를 문서 인스턴스 배열로 재설계 + 뷰어를 props 기반 다중
  인스턴스로 분리 + 워처/스크롤/검색의 인스턴스화 + 레이아웃 분할/리사이즈 필요.
  단일 문서 가정에 깊게 의존하는 현재 코드 기준 변경 범위가 크다.

## 6. 권고

1. **지금은 보류.** 우선순위는 `FEATURE-PROPOSALS.md` 로드맵(변경 하이라이트 → Quick
   Open → 폴더 검색 → 토큰)을 따른다. 비교 수요는 변경 하이라이트로 상당 부분 충족.
2. **멀티탭(Tier 2) 도입 시 재평가.** 멀티탭으로 스토어가 이미 다중 문서를 표현하게
   되면 스플릿의 한계 비용이 크게 줄어든다. 그때 다시 검토.
3. **(B) 편집|미리보기는 편집 모드 과제로 귀속.** 범용 창 분할로 풀지 않는다.

## 7. (도입을 결정할 경우) 최소 스코프 MVP

> 권고는 보류지만, 만약 강하게 요구될 때의 **최소 형태**.

- **2분할 좌|우, 비율 50:50 고정 또는 단일 드래그 핸들 1개**만. 3분할/그리드 금지.
- **두 페인 모두 "읽기 전용 뷰어"**로 한정. 편집은 범위에서 제외(편집 모드 과제).
- **멀티탭 선행.** 각 페인은 "현재 활성 탭/Quick Open으로 고른 문서"를 표시.
  탭 인프라 없이 단독 출시 금지.
- **스토어 최소 변경:** `currentFile/currentContent` 단수 가정을 깨지 않도록, 우선
  "보조 페인(secondaryFile/secondaryContent)" 1개만 추가하는 비대칭 모델로 시작.
  (정식 N-인스턴스 배열은 멀티탭과 함께.)
- **뷰어 인스턴스화:** `MarkdownViewer`가 스토어 직접 구독 대신 `file/content`를 props로
  받도록 리팩터링. 스크롤 위치·파일 워처·검색바를 인스턴스별로 보유.
- **레이아웃 충돌 가드:** 스플릿 활성 시 목차 패널 자동 닫기(폭 확보). 분할 상태에서
  본문 max-width를 페인 폭에 맞춰 완화.
- **크롬 최소:** 상단에 토글 아이콘 1개만 추가. 페인별 닫기 버튼은 페인 우상단에 hover로.
- **명시적 제외(MVP):** 동기 스크롤, 인라인 diff 하이라이트, 3+ 분할, 페인 내 편집,
  세션 복원 시 분할 레이아웃 저장.
