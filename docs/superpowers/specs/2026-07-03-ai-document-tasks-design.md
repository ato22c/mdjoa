# MD좋아 — AI 문서 작업(검토 · 개선 · 요점정리) 설계

- 날짜: 2026-07-03
- 상태: 설계 확정 (기본값 2건 + 진입점 + **확장성 우선** 사용자 승인 2026-07-03) → 구현 계획(writing-plans)
- 배경: AI가 만든 MD를 **확인·검토·개선**하는 용도가 MD좋아의 핵심 사용처. 이 작업을 로컬 `claude` CLI에 맡기고 결과를 분할창으로 받는다.
- **설계 원칙: 확장성.** 검토·개선·요점정리는 "AI 작업"의 첫 3개일 뿐이다. 이후 작업(커스텀 프롬프트, 톤 조정, 표 변환 등)을 **레지스트리에 한 줄 추가**로 늘릴 수 있게, 작업 정의를 데이터로 분리하고 실행 경로는 하나로 통일한다.

---

## 1. 목표

AI가 만든 마크다운 문서를 열어 놓은 상태에서, 메뉴 한 번으로 세 가지 작업을 로컬 `claude` CLI에 맡기고 **결과를 좌우 분할창(좌: 원문 / 우: 결과)** 으로 받는다.

- **검토(review)**: 문서의 문제점·개선점을 항목별로 **지적만** 한다(읽기 전용). 문서를 고치지 않는다.
- **개선(improve)**: 의미를 보존한 채 더 명확·정확하게 **다시 쓴 문서**를 돌려준다.
- **요점정리(summarize)**: 핵심만 **간결히 정리**한다.

이미 있는 "번역"의 자연스러운 형제 기능이다. 번역과 이 3작업은 본질이 같다 — **현재 문서를 프롬프트와 함께 claude CLI에 넘겨, 결과를 분할창으로 보여준다.**

## 2. 핵심 원칙 — 번역 인프라 재사용

번역 기능이 이 기능의 대부분을 이미 갖췄다. **새로 만들지 않고 일반화**한다.

| 재사용 대상 | 내용 |
|---|---|
| `src-tauri/src/commands/translate.rs` | `claude` 경로 탐지(`resolve_claude`)·spawn·취소용 PID 추적·`quiet`(Windows 콘솔 억제)·`strip_outer_fence`·인메모리 캐시 |
| `src/lib/translate.ts` | `claude` 존재 확인(`ensureClaude`)·응답 타임아웃·취소(`cancelTranslation`) |
| `src/components/viewer/TranslationView.tsx` | 좌/우 2-pane·복사·"새 파일로 저장"·스크롤 동기·보기/편집 토글 |
| `src/store/app.ts` | 결과 상태(`translatedDoc`)·`showTranslation`/`closeTranslation` |

### ⚠️ 재사용하면 안 되는 것 — 청크 분할 병렬 처리

`translate.ts`는 긴 문서를 `splitMarkdownForTranslation`으로 조각내 `mapLimit`으로 병렬 번역 후 이어붙인다. 이는 **번역이 조각별로 독립적**이라 유효하다. 하지만 이 3작업에는 **거짓**이다:

- **요점정리**: `요약(조각1) + 요약(조각2) ≠ 문서 전체 요약`. 조각 요약을 이어붙이면 엉터리.
- **검토**: 조각별 독립 검토는 **문서 전체를 가로지르는 문제**(가장 중요한 것)를 놓친다.
- **개선**: 조각별로도 대체로 되지만 전역 일관성을 잃는다.

→ **이 3작업은 문서 전체를 한 번에(single-shot) 호출한다.** 청크 로직은 번역 전용으로 남긴다.

## 3. 확장성의 핵심 — 범용 실행기 + 작업 레지스트리

확장성을 위해 **"무엇을 시킬지(작업 정의)"와 "어떻게 실행하는지(실행기)"를 분리**한다. 프롬프트·모델·출력 형태는 전부 TS의 **작업 레지스트리** 한 곳에 데이터로 모으고, Rust는 프롬프트를 받아 실행만 하는 **범용 실행기**가 된다.

**→ 새 AI 작업 추가 = 레지스트리에 항목 1개. Rust 변경 0. 메뉴·뷰 자동 반영.**

### 3.1 백엔드 (Rust) — 범용 실행기

- **커맨드를 하나로 통일**: 기존 `translate_markdown`(프롬프트를 Rust에서 조립)을 **`run_claude(prompt, model)`**(이미 완성된 프롬프트를 받아 실행)로 대체·일반화한다.
  - 재사용: `resolve_claude`·spawn·PID 등록·`quiet`·`wait`·`strip_outer_fence`·캐시 — 전부 그대로.
  - Rust는 **task가 무엇인지 모른다.** 프롬프트 문자열과 모델만 안다 → 새 작업이 생겨도 Rust 무변경.
- **캐시 키**: `hash(prompt || model)` — 같은 프롬프트·모델은 재호출 없이 즉시 반환. (프롬프트에 문서 본문·작업 지시가 다 들어가므로 자연히 작업·문서·모델을 구분함.)
- **취소**: PID 집합 `TranslateProc` → 공용 이름 `ClaudeProc`으로 격상, `cancel_translate` → `cancel_claude`. 모든 작업이 공유.
- **길이 가드(방어선)**: Windows `CreateProcessW` 명령줄 한계 때문에 Rust에 문자 수 상한 가드를 **유지**(신뢰 경계 방어). 프론트에서도 친절한 사전 안내(§3.2).

### 3.2 프론트엔드 — 작업 레지스트리 + 단일 실행 경로

- **작업 레지스트리** `src/lib/aiTasks.ts` — 단일 진실 원천(SSOT). 각 작업을 데이터로 선언:
  ```ts
  type OutputKind = "replace" | "critique" | "summary"; // 우측 창 버튼·스크롤동기 결정
  interface AiTask {
    id: string;                          // "review" | "improve" | "summarize" | "translate-ko" | ...
    labelKey: string;                    // i18n 키 (하드코딩 금지)
    model: "haiku" | "sonnet";           // 작업별 모델
    output: OutputKind;
    buildPrompt: (content: string) => string;  // 프롬프트 조립(§6)
    chunked?: boolean;                   // 번역만 true. 나머지는 단일 호출
  }
  export const AI_TASKS: AiTask[] = [ /* review, improve, summarize, translate-ko, translate-en */ ];
  ```
- **단일 호출 헬퍼** `runClaude(prompt, model)` = `invoke("run_claude")` + 타임아웃 + 취소. (지금 `translateChunk`에서 청크 프레이밍만 뺀 것.)
- **단일 진입 함수** `runDocumentTask(taskId)`:
  1. 레지스트리에서 작업 조회, `ensureClaude()` (없으면 기존 설치 안내)
  2. 결과 뷰 즉시 열기(스피너)
  3. `task.chunked`면 청크 루프(번역), 아니면 `buildPrompt(content)` **한 번에** `runClaude` 호출
  4. 결과를 스토어에 표시. 실패/타임아웃/취소는 기존 패턴(토스트 + 로그)
- 번역의 청크 분할(`splitMarkdownForTranslation`/`mapLimit`)은 **`chunked:true` 작업 전용**으로 남는다. 검토·개선·요점정리는 `chunked` 미설정 → 단일 호출(§2 근거).
- **28,000자 상한**: 초과 시 명확한 안내로 막는다(단일 호출 작업 한정, §5).

## 4. 상태 / 분할창

- 스토어 `translatedDoc`를 일반화: `taskDoc: { taskId: string; content: string } | null`. `showTranslation`은 `taskId:"translate-*"`로 흡수. (구체 작업 목록은 스토어가 아니라 레지스트리가 안다 → 스토어도 새 작업에 무변경.)
- **우측 창 버튼·스크롤 동기는 `OutputKind`가 결정**(레지스트리 조회). `TranslationView`(→ `TaskView`로 이름 일반화)는 task를 하드코딩하지 않고 `AI_TASKS[taskId].output`으로 분기:

| OutputKind | 예 | 우측 창 | 버튼 | 스크롤 동기 |
|---|---|---|---|---|
| `critique` | 검토 | 렌더된 지적/코멘트 | 복사 | 끔(원문과 1:1 대응 아님) |
| `replace` | 개선 · 번역 | 고쳐/바꿔 쓴 문서 | 편집/보기 토글 · **새 파일로 저장** · 복사 | 켬 |
| `summary` | 요점정리 | 짧은 요약 | 복사 · 새 파일로 저장 | 끔 |

- 좌측은 항상 원문. 헤더 라벨은 레지스트리 `labelKey`(i18n)에서. → **새 작업은 `OutputKind`만 고르면 뷰가 알아서 렌더**(뷰 무변경).

## 5. 프롬프트 (한국어 출력)

각 프롬프트는 레지스트리의 `buildPrompt(content)`에 산다(§3.2). 번역 프롬프트(`translate.rs:218`)와 같은 마커 방식(`===BEGIN DOCUMENT=== … ===END DOCUMENT===`)으로 본문을 감싸 `-p` 인자에 담는다. 모두 **한국어로 출력**, 코드/URL/링크/YAML 키/표 구조/LaTeX/`[[wikilink]]`는 건드리지 않도록 명시.

- **검토**: "다음 마크다운 문서를 검토하라. 문서를 **다시 쓰지 말고**, 문제점·개선점만 한국어로 항목별(우선순위 순)로 지적하라. 각 항목은 '무엇이/왜/어떻게 고치면 좋은지' 형태로."
- **개선**: "다음 마크다운 문서를 의미를 **보존한 채** 더 명확·정확하게 다시 써라. 마크다운 구조·헤딩·코드·링크를 유지하라. **개선된 문서만** 출력(설명·코멘트 금지, 전체를 코드펜스로 감싸지 말 것)."
- **요점정리**: "다음 마크다운 문서의 요점을 한국어로 간결히 정리하라. 핵심만. 목록·헤딩 사용 가능. 원문 길이의 일부로 압축."

## 6. 모델 / 설정

- 기본: 번역=`haiku`, 검토·개선·요점정리=`sonnet` (레지스트리 `model` 필드).
- 설정에 모델 override(선택 사항)를 둘 수 있으나 **v1에서는 레지스트리 기본값 고정으로 충분**(YAGNI). 필요 시 후속.

## 7. 진입점 (UI) — 통합 "AI 작업" 서브메뉴 (레지스트리 기반)

원래 두 안(①번역까지 통합 / ②별도 신설)을 검토한 결과, **①의 개선안**을 채택한다.

**함정**: 번역은 자체 하위 플라이아웃(한국어로/영어로)이 있어, 그대로 묶으면 `메뉴 → AI → 번역 → 한국어로`의 **3단 중첩**이 된다(마우스 호버 3단, 특히 Windows에서 취약).

**결정**: 번역 방향을 한 단계로 펴서 중첩을 없앤 **단일 "AI 작업" 서브메뉴**:

```
AI 작업 ▸
  ├ 검토
  ├ 개선
  ├ 요점정리
  ├ ──────────
  ├ 한국어로 번역
  └ 영어로 번역
```

근거: (1) 네 기능 모두 본질 동일("문서를 claude CLI에 맡겨 분할창으로 결과") (2) 3단 중첩 회피 (3) 메뉴 항목 1개로 정리 (4) 정식 배포 전이라 이동 비용 낮음. 기존 `HamburgerMenu.tsx`의 "번역" 단독 서브메뉴(253–285행)를 이 통합 메뉴가 흡수한다.

- **메뉴는 레지스트리를 순회해 그림**(`AI_TASKS.map`): 새 작업을 레지스트리에 넣으면 **메뉴 항목이 자동 생김**(HamburgerMenu 무변경). 구분선은 그룹 메타(예: `group: "task" | "translate"`)로.
- 노출 조건: `currentContent != null`일 때만(현재 번역과 동일).
- 아이콘: Lucide 단일 세트에서 하나(예: `Sparkles`/`Wand2`/`Bot`). 최종 라벨·아이콘·배치는 구현 단계에서 `ui-ux` 스킬 원칙으로 확정.
- **i18n**: 신규 UI 문자열은 진행 중인 `src/lib/i18n/`(feat/i18n) 모듈을 통해 ko/en 등록. 하드코딩 금지.

## 8. 거버넌스 (필수)

`CLAUDE.md`의 "네트워크 통신 금지" 예외 2는 현재 **"한↔영 문서 번역"에만** 한정돼 있다. 이 3작업은 같은 성격(사용자가 메뉴에서 직접 트리거·백그라운드/텔레메트리 아님·기존 로그인 사용·별도 과금 없음)이지만 **새로운 Anthropic 통신**이므로, 예외 조항 문구를 **"사용자가 메뉴에서 직접 트리거하는 AI 문서 작업(번역·검토·개선·요점정리 등)"으로 일반화·확장**한다(향후 작업까지 포괄). → 구현 계획에 `CLAUDE.md` 수정 포함(스펙만으로 끝내지 않음).

## 9. 확장성 검증 — 이후 새 작업을 추가하는 절차

이 설계가 실제로 확장 가능한지 "새 작업(예: 톤 조정)" 추가로 검증한다:

1. `src/lib/aiTasks.ts` `AI_TASKS`에 항목 1개 추가 — `{ id:"tone", labelKey:"aiTask.tone", model:"sonnet", output:"replace", buildPrompt }`.
2. `i18n/ko.ts`·`en.ts`에 라벨 키 1개씩.
3. 끝. — Rust(`run_claude`) 무변경, 메뉴(순회 렌더) 무변경, 뷰(`OutputKind` 분기) 무변경, 스토어(`taskId` 문자열) 무변경.

**BL-007 "커스텀 프롬프트"도 이 위에 얹힘**: `buildPrompt`가 사용자 입력을 받는 특수 작업 1개 + 입력 UI만 추가하면 됨(실행 경로·뷰·Rust 재사용).

**확장성을 위해 지키는 불변식**:
- Rust는 task를 모른다(프롬프트+모델만). 작업 정의는 레지스트리에만.
- 뷰·메뉴·스토어는 구체 작업 id를 하드코딩하지 않는다(레지스트리/`OutputKind` 경유).
- 새 출력 형태가 필요할 때만 `OutputKind`에 값을 추가(현재 3종으로 충분).
