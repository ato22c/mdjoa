## 🔄 업데이트 (2026-06-14) — 최종 결정: 멀티탭 드롭, "누적 없는" 3종 조합 채택·구현 완료

UX 재검토 결과, **누적형 멀티탭(①)을 채택하지 않기로** 결정했다. 사용자 페르소나의 실제 통증은 "여러 문서가 열려 **쌓이고** 복잡해진다(닫기 귀찮음)"인데, 탭이든 창이든 **누적되는 구조는 그 통증을 그대로 재현**한다. 집중을 높이는 해법은 *애초에 누적하지 않는 것*.

사용자의 3가지 니즈를 누적 없이 덮는 조합으로 대체했고 **모두 구현·검증 완료**:

| 니즈 | 해법 | 상태 |
|---|---|---|
| 잠깐 읽고 넘어가는 문서(대부분) | 단일 포커스 + 빠른 전환(QuickOpen·최근·위키링크) + **뒤로/앞으로 히스토리(⌘[ /⌘])** | ✅ `lib/navHistory.ts`, store nav, TopBar 버튼 |
| 늘 열어둘 문서(소수) | "탭으로 띄움"이 아니라 **"한 클릭 거리"** — 즐겨찾기/컨텍스트 섹션 | ✅ 기존 |
| 두 문서 비교(가끔) | **온디맨드 유니파이드 비교(⌘\\)** + 진짜 나란히는 **얇은 멀티윈도우** | ✅ `CompareView`+`lib/lineDiff.ts` / `open_in_new_window` |

**멀티탭(①)·인앱 창 분할(②)은 드롭/제외.** 멀티인스턴스(④)도 기존 결론대로 제외(single-instance 유지). 멀티윈도우(③)는 "얇게"만: 명령 1개("새 창에서 열기"), 보조 창은 세션 복원 비대상, 창 관리 UI 없음 → 크로스윈도우 store 동기화 이슈 회피(각 창이 자기 파일만 표시).

> 아래 원문 분석(①~④ 비교)은 의사결정 근거로 보존한다. "권장 결론"의 *1차 멀티탭*은 위 업데이트로 대체됨.

## 배경

- **타깃:** 많은 MD(CLAUDE.md/AGENTS.md, SKILL.md, 프롬프트, 설계문서, 태스크)를 오가며 AI 수정을 추적하는 개발자.
- **핵심 가치:** 간편함·빠른 실행·신뢰성. "콘텐츠 퍼스트 미니멀 / 기능 과잉 금지".
- **현재 코드 제약:**
  - `store/app.ts`가 `currentFile`/`currentContent` **스칼라 단수** — 두 번째 문서를 담을 구조가 없음.
  - `tauri-plugin-single-instance` 사용 — **단일 OS 프로세스 강제**(두 번째 실행은 argv를 기존 `main` 창으로 전달하고 종료). 파일 연결(.md 더블클릭) 라우팅이 여기 의존.
  - 설정·즐겨찾기·최근·로그는 모두 `<appdata>/com.fusionsoft.mdjoa/*.json` **단일 파일 + atomic write(tmp→rename)**.

## "여러 문서를 본다"의 4가지 축

| 옵션 | 정의 | 가치 | 복잡도 | 핵심 리스크 |
|---|---|---|---|---|
| **① 멀티탭** | 한 창, 여러 탭 | 높음 | 중 | store 인스턴스화 필요 |
| **② 창 분할** | 한 창, 좌\|우 페인 | 중 | 중상 | 760px 본문폭/크롬 경합, 편집모드와 중복 |
| **③ 멀티윈도우** | 한 프로세스, 여러 WebviewWindow | 중상 | 상 | **창마다 독립 JS store** → 크로스윈도우 상태 동기화 |
| **④ 멀티인스턴스** | 여러 OS 프로세스 | 낮음 | 상 | **appdata JSON write 경합**, single-instance와 충돌 |

### ④ 멀티인스턴스 — 제외 권장 ❌
- 각 프로세스가 같은 `*.json`(설정/즐겨찾기/최근)을 **독립적으로 atomic write** → tmp→rename이 프로세스 내에선 안전해도 **프로세스 간엔 last-writer-wins**로 변경 유실(예: A창에서 추가한 즐겨찾기를 B창이 덮어씀).
- `single-instance` 플러그인을 제거해야 하는데, 그러면 **파일 연결 라우팅**(OS에서 .md 열 때 기존 창으로 모으기)이 깨짐.
- 리소스도 N배. → **단일 인스턴스 유지가 정답.**

### ③ 멀티윈도우 — "두 문서 비교"의 더 나은 해법 (②보다 우선 고려)
- **같은 프로세스 안에서 새 `WebviewWindow`**를 띄움(멀티인스턴스 아님). OS-네이티브 창 관리 + **멀티모니터** 지원.
- ②창 분할 대비 장점: 인앱 크롬(분할 핸들/레이아웃)을 **안 늘려** 콘텐츠-퍼스트에 부합. Windows(메인 타깃)에서도 자연스러움.
- **catch: 각 WebviewWindow는 독립 JS 컨텍스트라 Zustand store가 창마다 따로다.** 공유 상태(테마/즐겨찾기/최근)는 동기화 설계 필요(아래).

### ② 창 분할(인앱) — 멀티윈도우가 있으면 사실상 불필요
- "두 문서 비교"는 ③로, "편집|미리보기"는 **다른 세션이 만드는 편집 모드**로 흡수됨 → 인앱 분할의 고유 가치가 작음.
- 도입한다면 멀티탭 위에 **2분할 좌\|우 50:50 + 핸들 1개**만(3분할·동기스크롤 제외). 그러나 **우선순위 최하 / 보류 권장.**

### ① 멀티탭 — 1차 구현 대상 ✅
- AI 워크플로의 본질(여러 MD 동시 참조). 단일 창·단일 store라 **동기화 이슈 없음** → 가장 단순하고 가치 높음.

## 권장 결론

1. **단일 OS 인스턴스 유지**(single-instance 플러그인 유지). 멀티인스턴스 제외.
2. **1차: 멀티탭** (한 창, 탭).
3. **2차(선택): 멀티윈도우** — "두 문서 비교/멀티모니터" 수요가 확인되면. **인앱 창 분할(②)은 멀티윈도우로 대체하고 제외**하는 쪽을 권장(기능 과잉 방지).
4. 멀티윈도우를 안 하기로 하면, 그때만 ②최소 2분할을 검토.

## 멀티탭 구성 (1차)

```ts
// store
tabs: Tab[]            // { id, path, title, scroll, isDirty }
activeTabId: string | null
// MD는 작음 → 열린 탭 content는 메모리 캐시(즉시 전환)
```
- **호환 시프트:** 기존 컴포넌트가 다 `currentFile`/`currentContent`를 읽으므로 이 둘을 **활성 탭의 파생값**으로 노출 → 변경 최소화.
- **열기:** 새 탭, **이미 열려 있으면 포커스**(중복 금지). preview-tab 등 복잡 패턴 제외.
- **닫기:** `⌘W`=활성 탭 닫기, 0개가 되면 창 닫기(현재 메뉴 `⌘W`=Close Window 재배선 필요).
- **전환:** `Ctrl+Tab` / `⌘1~9`.
- **dirty:** 편집모드 `isDirty`를 **탭 단위**로 → 탭 점 표시 + 미저장 닫기 시 `ask` 확인.
- **세션 복원:** 열린 탭 경로를 settings에 저장 → 재실행 복원.
- **UI:** TopBar 아래 **얇은 탭 스트립, 탭 ≥2일 때만 표시**(1개면 숨겨 미니멀 유지).

## 멀티윈도우 구성 (2차, 도입 시)

- **새 창 = 같은 프로세스의 `WebviewWindow`** (Rust 커맨드로 생성). 멀티탭에서 한 **`MarkdownViewer`의 props(문서 인스턴스)화**를 그대로 재사용.
- **크로스윈도우 상태 동기화 (핵심 설계):**
  - **appdata JSON = 단일 진실원**. 모든 쓰기는 **Rust 커맨드 경유**(이미 그러함) → **프로세스 내 직렬화**라 ④와 달리 race 없음.
  - 변경 시 Rust가 **전역 이벤트**(`settings-changed`/`favorites-changed`/`recent-changed`) emit → **모든 창이 구독해 갱신**. (간단 대안: 창 focus 시 재로드.)
- **파일 라우팅:** `RunEvent::Opened` / single-instance argv → 현재는 `main` 창으로 emit. 멀티윈도우 시 **"마지막 포커스 창"을 추적**해 그 창의 새 탭으로.
- 분할 진입(만약 ② 별도 채택 시)엔 목차 패널 자동 닫기.

## 구현 순서 & 협업 주의 ⚠️

1. **편집 모드(다른 세션) 머지 대기** — 멀티탭의 탭별 dirty가 그 위에 얹힘.
2. **멀티탭** — `store/app.ts` 인스턴스화 + `MarkdownViewer` props화. **이 두 파일을 지금 다른 세션이 수정 중**이라 반드시 **그쪽 일단락 후**, 가능하면 단일 세션에서.
3. (선택) **멀티윈도우** — props화 재사용 + 크로스윈도우 동기화.
4. **인앱 창 분할**은 멀티윈도우 도입 시 제외, 미도입 시에만 최소 2분할 검토.
