# Work Handoff (작업 핸드오프)

집에서 하던 작업을 사무실에서, 또는 그 반대로 **그대로 이어받기** 위한 스킬입니다.
한쪽에서 끝낼 때 코드와 컨텍스트를 GitHub에 올려두고, 다른 쪽에서 그걸 내려받아 중단했던
지점부터 이어서 작업합니다.

핵심 통찰: **이어받는 쪽의 Claude는 직전 대화를 전혀 모르는 "백지 상태"입니다.**
그래서 `git pull` 만으로는 부족하고, "왜 지금 이 코드가 이런 모양인지"까지 담은
핸드오프 문서(`.handoff/HANDOFF.md`)가 두 세션을 잇는 유일한 다리입니다. 이 문서를 잘 쓰는 것이
이 스킬의 전부라고 봐도 됩니다.

## 두 가지 모드

| 모드 | 언제 | 사용자 신호 (예) |
|------|------|------------------|
| **마무리 (handoff-out)** | 한 장소에서 작업을 끝내고 떠날 때 | "마무리하고 푸시", "퇴근 전 정리", "핸드오프", "이거 넘겨줘" |
| **이어받기 (resume)** | 다른 장소에서 작업을 시작할 때 | "이어서 하자", "집에서 하던 거 이어받자", "어제 작업 계속", "resume" |

신호가 모호하면 어느 쪽인지 한 번 물어보세요. 막 도착해서 "시작하자"는 보통 **이어받기**,
한참 작업한 뒤 "이제 그만"은 보통 **마무리**입니다.

---

## 모드 A — 마무리 (handoff-out)

### 1. 현재 상태 파악
저장소 루트와 브랜치, 변경 사항을 확인합니다.

```bash
git rev-parse --show-toplevel        # 저장소 루트
git branch --show-current
git status --short
git log --oneline -8
git diff --stat
```

`.handoff/` 가 `.gitignore` 에 걸려 있지 않은지 확인하세요. 걸려 있으면 동기화가 안 되므로
사용자에게 알리고 예외 처리를 제안합니다. (`.handoff/` 파일은 **반드시 커밋되어** 원격에 올라가야
다른 장소에서 보입니다.)

### 2. 이번 세션 요약 + 완료 여부 판단
대화 기록과 `git diff` 를 근거로 **이번 세션에 무엇을 했는지** 정리하고, 작업이 **완료**됐는지
**진행 중**인지 판단합니다. 이 판단이 뒤의 커밋·PR 방식을 가릅니다.

### 3. 변경 커밋 (append-only 원칙)
- **완료된 단위**는 의미 있는 메시지로 정상 커밋합니다.
- **진행 중/미완성**이면 `WIP: <무엇을 하던 중인지>` 형태로 커밋합니다. 미완성이어도
  커밋해서 push해야 다른 장소에서 그 변경을 받을 수 있기 때문입니다.

> **중요 — 히스토리를 다시 쓰지 마세요.** `git reset`, `git commit --amend`, force-push 는
> 쓰지 않습니다. 한 번 push한 WIP 커밋은 이미 원격(=다른 컴퓨터)에 존재하므로, 그걸 되돌리면
> 두 컴퓨터의 히스토리가 어긋나고 force-push가 필요해집니다. 대신 **항상 그 위에 새 커밋을 쌓는**
> append-only 방식을 씁니다. 지저분해 보이는 WIP 커밋들은 나중에 PR을 머지할 때 squash로
> 한 번에 정리하면 됩니다.

### 4. 핸드오프 문서 작성 — 이 스킬에서 가장 중요한 단계
`.handoff/HANDOFF.md` 를 **덮어쓰고**(항상 최신 상태 1개만 유지), `.handoff/worklog.md` 에는
이번 세션 항목을 **덧붙입니다**(누적 기록).

`HANDOFF.md` 는 **직전 대화를 전혀 모르는 사람**이 읽는다고 생각하고 쓰세요. "다음 할 일" 목록만
나열하면 안 됩니다. 목표가 무엇이고, 어떤 제약이 있고, **시도했다가 버린 접근**이 무엇이며,
**지금 이 미완성 코드가 왜 이런 모양인지**까지 적어야 이어받는 Claude가 같은 함정에 다시 빠지지 않습니다.

아래 `.handoff/` 파일 구조 섹션의 템플릿을 사용하세요.

### 5. 핸드오프 문서 커밋
코드 커밋과 분리해 별도로 커밋하면 나중에 알아보기 쉽습니다.

```bash
git add .handoff/
git commit -m "chore(handoff): 세션 핸드오프 업데이트"
```

### 6. push (그리고 필요하면 PR)
원격에 이 브랜치가 이미 있으면 먼저 받아 충돌 가능성을 줄이고, 첫 push면 `-u` 로 업스트림을 설정합니다.

```bash
# 업스트림(추적 브랜치)이 있을 때만 pull. 새 브랜치라면 받을 게 없으므로 건너뜀.
if git rev-parse --abbrev-ref --symbolic-full-name @{u} >/dev/null 2>&1; then
  git pull --ff-only        # 다른 장소에서 올려둔 변경이 있으면 먼저 받음
fi
git push -u origin "$(git branch --show-current)"   # -u: 다음부터 pull/push가 추적 정보를 인식
```

- 새 브랜치에서 업스트림 설정 없이 `git pull` 을 부르면 "추적 정보 없음" 에러가 납니다. 그래서
  pull은 업스트림이 있을 때만 하고, push에는 항상 `-u` 를 붙여 한 번에 추적 정보를 설정합니다.
- `git pull --ff-only` 가 실패하면(히스토리 갈라짐) 멈추고 사용자에게 상황을 설명하세요.
  임의로 merge/rebase 하지 마세요.
- **PR은 작업이 실제로 완료됐을 때만** 일반 PR 옵션을 제시합니다. 2단계에서 "진행 중"으로
  판단했다면 일반 PR을 만들지 말고 **브랜치 push만** 하거나, 사용자가 원하면 **draft PR**로 올립니다.
  반쯤 된 작업으로 리뷰용 PR을 여는 건 의미가 없기 때문입니다.
- 작업이 완료됐다면 push만 할지 PR을 만들지 사용자에게 물어보세요. PR은 `gh pr create` 사용
  (이미 있으면 새로 만들지 말고 그대로 둠).

### 7. 마무리 안내
브랜치명과, 다른 장소에서 이어받는 방법을 한 줄로 알려주세요.
예: "`feature/login` 에 push 완료했습니다. 다른 컴퓨터에서 그냥 '이어서 작업하자'라고 하면 됩니다."

## 모드 B — 이어받기 (resume)

### 1. 최신 상태 가져오기
```bash
git rev-parse --show-toplevel
git fetch
```

`.handoff/HANDOFF.md` 가 가리키는 브랜치로 이동한 뒤 최신 커밋을 받습니다.

```bash
git checkout <핸드오프-브랜치>
git pull --ff-only
```

- `HANDOFF.md` 가 아직 없으면(처음이라 핸드오프 기록이 없음) pull만 한 뒤, `git log` 와
  `git status` 로 현재 상태를 요약해 주고 일반적인 작업 모드로 진행합니다.
- `git pull --ff-only` 가 충돌로 실패하면 멈추고 사용자에게 알리세요. 마지막 핸드오프 이후 이쪽
  컴퓨터에서 따로 커밋한 게 있을 수 있습니다.

### 2. 컨텍스트 복원 — 읽기만 하지 말고 흡수하세요
`.handoff/HANDOFF.md` 와 `.handoff/worklog.md` 최근 항목을 읽고 **머릿속에 작업 맥락을 재구성**합니다.
목표, 제약, 버린 접근, 현재 미완성 부분이 왜 이런지, 다음 할 일을 파악하세요. 단순히 파일 내용을
사용자에게 출력하는 게 아니라, 그 내용을 근거로 **바로 이어서 작업할 수 있는 상태**가 되어야 합니다.

### 3. 짧게 브리핑
사용자에게 어디서 이어받는지 3~4줄로 정리해 줍니다.
예: "여기서 이어받습니다 — 브랜치 `feature/login`, 마지막 작업: 로그인 폼 검증 추가(WIP).
다음 할 일: 비밀번호 규칙 에러 메시지 연결. 참고: bcrypt 대신 argon2 쓰기로 결정했었음."

### 4. 이어서 작업
- 마지막 커밋이 `WIP:` 라면 그 변경은 이미 작업 트리/히스토리에 반영돼 있습니다. **그 위에 새 커밋을
  쌓으며** 이어가세요. (앞서 말한 append-only 원칙 — 여기서도 `reset`/`amend` 금지. 이미 push된
  커밋입니다.)
- `HANDOFF.md` 의 "다음 할 일" 첫 항목부터 바로 착수합니다.

## `.handoff/` 파일 구조

저장소 루트에 `.handoff/` 폴더를 둡니다.

```
.handoff/
├── HANDOFF.md     # 항상 최신 상태 1개 (매번 덮어씀) — 이어받기의 핵심
└── worklog.md     # 세션별 누적 기록 (항상 맨 위에 새 항목 추가)
```

### HANDOFF.md 템플릿

```markdown
# 작업 핸드오프

> 마지막 업데이트: <YYYY-MM-DD HH:MM> · <장소/컴퓨터 이름>
> 이어받는 곳: 이 문서를 읽고 "다음 할 일"부터 진행하세요.

## 현재 상태
- 브랜치: `feature/...`
- 마지막 커밋: `<해시 짧게> <메시지>`   <!-- WIP면 "⚠️ WIP — 위에 새 커밋을 쌓아 이어가세요" -->
- 작업 트리: 클린 / 변경 있음

## 목표 (이 작업으로 무엇을 이루려 하나)
- ...

## 이번 세션에 한 일
- ...

## 진행 중 / 미완성
- 어떤 파일에서 무엇을 하던 중이었는지. 관련 `TODO` 주석 위치 등.

## 다음 할 일
1. ...
2. ...

## 알아둘 것 (결정·제약·함정)
- 내린 결정과 그 이유 (예: "bcrypt 대신 argon2 — 사내 표준").
- 시도했다 버린 접근과 이유 (같은 실수 반복 방지).
- 알려진 함정 / 막혔던 지점.

## 이어받기 명령
\`\`\`bash
git fetch && git checkout feature/... && git pull --ff-only
\`\`\`
```

### worklog.md 항목 형식 (맨 위에 추가)

```markdown
## <YYYY-MM-DD HH:MM> · <장소>
- 한 일 요약
- 남긴 상태: (완료 / WIP — 무엇이 남았는지)
```

장소/컴퓨터 이름은 `hostname` 또는 `scutil --get ComputerName`(macOS)으로 자동 채우고,
사용자가 "집"/"사무실"처럼 부르면 그 표현을 우선 쓰세요.

## 핵심 원칙 (왜 이렇게 하나)

1. **append-only, 히스토리 보존.** 두 컴퓨터가 같은 원격 브랜치를 공유하므로, 한쪽에서 push한
   커밋을 다른 쪽에서 `reset`/`amend`/force-push로 되돌리면 곧바로 히스토리가 갈라집니다.
   항상 새 커밋을 쌓는 방식이 어긋남을 원천 차단하고, 정리는 PR squash 한 번으로 끝냅니다.

2. **컨텍스트 문서가 제품이고 `git pull`은 그저 거들 뿐.** 이어받는 세션은 직전 대화를 모릅니다.
   `HANDOFF.md` 의 "왜"(결정·제약·버린 접근)가 빠지면 이어받는 쪽이 같은 시행착오를 반복합니다.
   가장 공들여 쓸 곳은 코드 커밋 메시지가 아니라 이 문서입니다.

3. **미완성은 숨기지 말고 넘긴다.** 깔끔한 커밋만 push하면 미완성 변경이 한쪽 컴퓨터에 갇힙니다.
   WIP 커밋으로 묶어 올리는 편이, 다른 장소에서 "그대로 이어받기"라는 목표에 맞습니다.

## 엣지 케이스

- **저장소가 아님 / 어느 저장소인지 모호함** → 먼저 확인하고 진행하세요.
- **`gh` 미인증** → PR 단계에서만 문제. `gh auth status` 로 확인하고, 안 되면 push까지만 하고
  사용자에게 알리세요.
- **`.handoff/` 가 gitignore됨** → 동기화 불가. 사용자에게 알리고 제외 규칙 조정을 제안하세요.
- **pull 충돌** → 자동으로 merge/rebase 하지 말고 멈춰서 사용자에게 상황을 설명하세요.
- **핸드오프 기록 없음(첫 사용)** → 이어받기 모드에서 pull 후 git 상태 요약으로 대체합니다.

## 이 스킬을 두 컴퓨터에서 쓰려면

이 스킬 자체도 양쪽 컴퓨터에 있어야 합니다. 가장 깔끔한 방법은 **프로젝트 저장소 안**
`.claude/skills/work-handoff/` 에 두고 커밋하는 것입니다. 그러면 `git pull` 할 때 스킬까지 함께
따라오므로 다른 컴퓨터에서 저장소만 받으면 바로 쓸 수 있습니다. (`~/.claude/skills/` 에만 두면
컴퓨터마다 따로 설치해야 해서, 이 스킬이 풀려는 문제를 그대로 다시 만나게 됩니다.)
